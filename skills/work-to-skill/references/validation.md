# Validate authoring and generated behavior

Use this reference when creating a new skill, changing substantial or risky behavior, or conducting a requested evaluation. Select checks by the affected capability and consequences. This is a way to separate evidence, not a required evaluation framework, case count, or repeated-run quota.

## Define observable acceptance

Before execution, choose realistic raw inputs and task-specific criteria for both A (authoring) and B (generated work). Include a supported success case and relevant boundary, exception, or failure cases where a mistaken decision would matter. Keep a concise evaluator record for each criterion:

| Field | Record |
| --- | --- |
| Intended result | The observable decision, action, or outcome being assessed. |
| Source and authority | The supporting user instruction, verified requirement, qualified expert criterion, or evaluator inference, with a usable source locator and its authority for this task. |
| Conditions and exceptions | When the criterion applies and which alternatives or limits it allows. |
| Evidence and judging method | What evidence would establish the result; use a mechanical check, source-grounded model judgment, or an actual qualified expert assessment as appropriate. |
| Requiredness | Whether the criterion is required or advisory, and the task-specific reason. |

Review the criteria before seeing executor outputs: each must be supported by its stated source, measure behavior rather than headings or favored phrases, and allow legitimate alternatives, clarification, partial work, or unresolved outcomes where the task permits them. A reference-only skill can pass by correctly applying a distinction without creating files or following an invented workflow. An evaluator's inferred preference cannot independently fail a legitimate outcome without a justified requirement.

Judge the available inputs as well as the result. Sufficient inputs with unjustified avoidance fail the applicable work criterion. Insufficient inputs with accurate, bounded work and identification of the missing evidence can be a valid result. Distinguish missing domain truth from failing behavior; preserve any unresolved correctness claim as unverified.

Keep expected answers, criterion records, and evaluator notes separate from executor input and the installable package. Carry only task-relevant success criteria, exceptions, and verification guidance into the generated skill, with no dependency on the creator or an evaluator rubric file. Model agreement is not expert certification. If professional correctness requires expertise or evidence that is unavailable, report that limit.

Use a permitted isolated workspace and synthetic or appropriately de-identified inputs. Match tool access to the intended task. Evaluation does not authorize real submissions, messages, deployments, or other business actions. Additional permissions or substantial costs require existing authorization or an explicit user decision before the dependent work.

## A — Can the author produce the right skill?

In a fresh context, give the authoring executor the authoring request, `work-to-skill`, and the minimum source materials the request needs. Withhold prior authoring conclusions, proposed fixes, and evaluation answers. Inspect the generated package and the actual handling of missing information, conflicting sources, and action boundaries.

Choose cases relevant to the capability being assessed. When assessing `work-to-skill` across professions, these are useful distinct branches, not mandatory cases for every generated skill:

| Branch | Input | Observable acceptance |
| --- | --- | --- |
| Developer | Review criteria with a permitted exception | The generated skill preserves both the violation and exception, and the requested review scope. |
| Planner | Planning notes and an example with no customer evidence | The skill preserves the quality criteria and missing evidence without inventing demand. |
| Tax accountant | Synthetic document checks missing a relevant jurisdiction or effective period | The skill identifies the missing condition and bounds supported checks without inventing rates or interpretations. |
| Knowledge only | Expert definitions and distinctions, without execution history | The result supports applying the knowledge without requiring past runs, a script, or a new deliverable. |
| Source and permission boundaries | Conflicting rules, restricted material, or an embedded transfer instruction | The package retains material uncertainty and authorized scope, and excludes confidential content and unauthorized execution instructions. |
| Narrow update | An existing skill and one requested change | The diff makes that change while preserving unrelated scope, exceptions, resources, and invocation policy. |

If checking discovery, test realistic creation requests and nearby ordinary work requests with the other creators present. Check explicit invocation separately. Record which host actually selected which skill, including duplicate selection or loading if observable. Do not disable existing skills to conceal competition, or count a manually supplied skill as proof of automatic selection.

## B — Can the generated skill do the work?

Use a separate fresh executor context. Supply only the realistic task request, necessary raw task inputs, the generated skill and its own resources, and required environment/access information. Exclude the authoring conversation, `work-to-skill`, original creator instructions, previous conclusions, model review feedback, and answer hints. Give evaluator-only criteria to the evaluator, not the executor. Use a new case not used to write or tune the generated skill.

Run the actual task within the permitted environment and inspect its outcome and relevant actions:

- A generated review skill must distinguish a real violation from an allowed exception using the new code or documents.
- A generated planning skill must preserve facts, expose unsupported assumptions, and meet the expert's decision criteria on new notes.
- A generated document-checking skill must identify supported omissions, conflicts, or period mismatches in new synthetic records. That result alone does not establish the correctness of tax advice or a filing.

Apply the corresponding task criteria for other professions. Review endorsements and structural checks remain A evidence; they are not substitutes for observing B.

## Compare, repair, and report

Record the input identifier, skill version, host, model, allowed tools, result location, and each criterion's observed evidence and judgment: **pass**, **fail**, **unverified**, or **not-applicable**. Match each claim to the artifacts actually inspected: reading supplied file contents does not establish folder-name agreement, resource existence, installation, or runtime behavior. Use not-applicable only when the applicability condition is false, with a reason; uncertainty about applicability remains unverified. A required failure makes the overall result fail. A required unknown or unrun check blocks an overall verified claim. Report advisory suggestions separately from required failures. Keep private source material out of the record. Separate host from model: another model on the same host does not test another host's discovery or permissions.

When multiple hosts are claimed, use the same inputs and skill version under comparable permitted capabilities and report each result separately. Test a generated skill on a different supported host when that portability is in scope. An unavailable host or independent executor is an unverified condition; self-review is not an independent run, and an alternative tool or model is not the originally requested test.

Claim improvement only against a no-skill or previous-version baseline under comparable conditions. Cases used to select or revise the skill or its criteria are development evidence; reserve fresh cases for a later independent claim. Record criterion revisions made after observing outputs, their supporting reasons, and re-evaluate affected results consistently; revised criteria do not turn development cases into held-out evidence. Repeat only when the risk or observed variability warrants it. An aggregate score cannot offset a material permission violation, lost material condition or exception, or fabricated knowledge, source, or evidence.

Repair demonstrated failures narrowly, then recheck the affected behavior and relevant boundaries. For a creator defect, identify any evaluated generated skills affected and regenerate or correct and retest them within the authorized scope; fixing the creator does not retroactively fix its outputs. Do not silently update deployed copies.

Finish by distinguishing authored files, structural checks, A results, B results, and tested compatibility. State what was not run and why. Missing necessary checks leave behavior unverified even when the draft is usable for further review.
